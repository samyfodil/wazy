# wazy.dev

The documentation site, built with [Astro](https://astro.build) and
[Starlight](https://starlight.astro.build) and deployed to GitHub Pages by
[`.github/workflows/pages.yaml`](../.github/workflows/pages.yaml).

```bash
npm ci
npm run dev        # http://localhost:4321/wazy/
npm run build      # -> dist/
npm run check:links
```

## Layout

```
src/
  pages/index.astro        the landing page (custom, not a docs page)
  styles/brand.css         the whole design system; there is no other custom CSS
  content/docs/
    introduction.md        Start here
    getting-started.md
    examples/              one tutorial per runnable example in ../examples
    guides/                conceptual reference
    reference/
astro.config.mjs           site, base, sidebar
ec.config.mjs              Expressive Code (code block) options
check-links.mjs            resolves every internal href against dist/
```

## Three things that will bite you

**Relative links are not rewritten for `base`.** The site is served under `/wazy/`, and Astro
emits relative markdown links verbatim. Write them relative to the *served URL*, not to the
source file: from `src/content/docs/examples/wasi.mdx` (served at `/wazy/examples/wasi/`), the
guides are at `../../guides/`, not `../guides/`. `npm run check:links` resolves every internal
href against the built tree and is the only thing standing between you and a wall of 404s — the
Pages workflow runs it after every build.

**Changing `ec.config.mjs` invalidates the code-block stylesheet, but not Astro's cached page
output.** Pages rendered before the change keep a `<link>` to the old hash, which no longer
exists, and their code blocks render unstyled. A clean `dist/` is not enough. Clear the caches:

```bash
rm -rf dist .astro node_modules/.astro node_modules/.vite && npm run build
```

CI does a fresh checkout, so this never ships — it only makes local builds silently wrong.
`check:links` catches it, because it checks asset URLs too.

**The repo root `.gitignore` ignores `package-lock.json`** (a rule meant for AssemblyScript
testdata). `website/.gitignore` negates it, because `npm ci` in the Pages workflow needs the real
lockfile. Don't remove that negation.

## Conventions

- The landing page is the only `.astro` page. Everything else is `.md` or `.mdx` in the docs
  collection; use `.mdx` when you need `<Tabs>`, `<Steps>` or another Starlight component.
- In `.mdx`, a bare `<` or `{` in prose is a syntax error that fails the build. Backtick generic
  types: `` `stream<T>` ``, `` `result<T, E>` ``.
- Colour carries meaning rather than decoration: `--wz-cyan` marks a capability that was granted
  or a number that was measured. Grey is denied or unmeasured. Don't spend cyan on anything else.
- Mono (`--sl-font-mono`) is for machine text — code, capability names, measured values. Not for
  labels that just want to look technical.
- Every number on the site is a benchmark in this repository. If you cannot point at the test
  that produced a figure, don't publish the figure.
- The `Examples` sidebar group is autogenerated from `src/content/docs/examples/`, ordered by
  each page's frontmatter `sidebar.order`.
